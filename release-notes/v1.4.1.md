## v1.4.1 — Stop the samples-endpoint log flood on Python 3.14

A maintenance release that fixes an unhandled exception on the samples POST. On installs running a recent aiohttp (as shipped with Home Assistant on Python 3.14), every samples payload whose body wasn't zlib-wrapped raised a `RequestPayloadError`, which filled `home-assistant.log` with `aiohttp.server` tracebacks and silently dropped the sample.

### Fixes

- **Unhandled `RequestPayloadError` on `POST /v3/samples`.** The Curb hub sends `Content-Encoding: deflate`, but the body is raw DEFLATE or plain MessagePack — not the zlib-wrapped format aiohttp's decompressor expects. Newer aiohttp auto-inflates the body *at parse time*, so it raised (`Error -5 unsupported compress method` / `Error -6 incorrect checksum`) before `_handle_samples` ran, and the decoder's own inflate fallback was never reached. The server now runs with `auto_decompress=False` and decodes the raw bytes itself: MessagePack first, then an explicit inflate covering both zlib and raw-deflate framings. Affected samples are now ingested instead of dropped.
- **Guarded body read.** Any remaining read failure returns a single `400` with a one-line warning rather than an unhandled exception, so a malformed request can't flood the log.

### Upgrade notes

- No action required. The fix applies on the first samples POST after you upgrade and restart Home Assistant. No config, storage, or entity changes.
- If your log was flooding before the upgrade, the `aiohttp.server` / `RequestPayloadError` entries stop growing once the new code is running.

### Caveats

- This addresses the decode/exception path only. If a hub genuinely sends a corrupt body, it's still answered with a `400` and a single warning line (by design) rather than being silently accepted.
